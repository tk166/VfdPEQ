## 整体架构

一套 eqMac 式的系统级 PEQ 大致由三部分组成：

| 模块 | 难度 | 说明 |
|---|---|---|
| 系统音频捕获/回注 | ⭐⭐⭐⭐ | 核心难点，见下文路线选择 |
| PEQ 滤波引擎 | ⭐⭐ | RBJ biquad 公式 + numpy，一两天能写完；macOS 还自带 `kAudioUnitSubType_NBandEQ` AudioUnit 可直接用 |
| Dear PyGui 界面 | ⭐ | 拖点画曲线、频响实时预览，DPG 的 Plot API 很适合 |

## 系统级音频的三条技术路线

**路线 A：虚拟音频驱动（eqMac 本尊的方案）**
通过 Apple 的 Audio Server Plug-In（用户态驱动）建一个虚拟输出设备，把系统默认输出指向它，处理后再送到真实设备。eqMac 本身是开源的（GPL 协议）可以直接参考，Apple 也有官方示例文档。
- 优点：效果最“原生”，延迟可控，开机即用
- 缺点：必须用 C/C++ 写驱动层，代码要签名+公证；这是三条路里工程量最大的

**路线 B：Core Audio Process Tap（macOS 14.4+，推荐你关注）**
Apple 在 14.4 引入了 `AudioHardwareProcessTap` API，**不需要装任何驱动**就能捕获系统全局音频，可以设置 mute 原始输出、由你的 app 处理后重新播放。insidegui 的开源项目 AudioCap 就是基于它做的系统音频录制，Apple 也有官方教程。
- 优点：不用写驱动、不用装内核组件，是 2024 年后做这类工具的最短路径
- 缺点：要求 macOS ≥ 14.4；tap 回放会引入额外延迟（听音乐无感，看视频对口型会有轻微影响）；需要一定的签名配置

**路线 C：现成虚拟声卡 + Python 的“懒人混合方案”**
直接用免费的 BlackHole 虚拟设备做系统输出，Python 用 `sounddevice` 从 BlackHole 读音频 → numpy 跑 PEQ → 播放到真实设备。不用碰任何驱动代码，**纯 Python 就能跑通全链路**，缺点是多一跳、延迟稍高。

## 关于 Dear PyGui + Python 的可行性

- GUI 完全没问题，DPG 画 30 段 PEQ 曲线 + 拖拽频点非常轻松
- 实时音频处理用 Python 也够：EQ 只是几个 biquad 级联，按 256~1024 帧一块做 numpy 向量化运算，CPU 占用很低；热路径别放纯 Python 循环即可
- 如果选路线 B，tap 那层 API 目前 Python 绑定不完善，建议写一个几十行的小 Swift helper 负责捕获，通过 BlackHole/管道喂给 Python —— 架构上很干净

## 我的建议路线图

1. **第 1 周**：BlackHole + sounddevice + numpy biquad，先跑通“全系统声音经过你的 EQ 再出来”
2. **第 2 周**：Dear PyGui 做界面（频段拖点、频响曲线、预设保存 JSON）
3. **之后**：如果想去掉 BlackHole 依赖、降低延迟，再把捕获层换成 Process Tap 或自研 Audio Server Plug-In

总体评估：**个人自用、全免费 —— 完全可行**，最省力的组合是“BlackHole（或 Process Tap）+ numpy + Dear PyGui”；只有当你想要 eqMac 那种商业级体验（自动接管默认输出、低延迟、免手动配置）时，才需要啃驱动那一层硬骨头。
